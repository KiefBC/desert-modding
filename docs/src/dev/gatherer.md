# Gatherer internals

Sources: `crates/desert-harvest/src/gatherer/entry.rs`, `hook.rs`, `catch.rs`, `dump.rs`, `crates/desert-harvest/src/entry.rs`, `crates/desert-core/src/gimmick.rs`, `crates/desert-core/src/creature.rs`, `CLAUDE.md` (How the gatherer works). Evidence: `docs/reference-internals.md` §16, §17, §19.6.

## The record-loader hook

One hook, no polling. `desert_core::gimmick` finds the `gimmickinfo` record loader in the running image by content, through the accessor that names `gimmickinfo` (one accessor scan without an image base). The gatherer is one half of `desert-harvest`. `gatherer::entry::install_loader_hook` checks the 12 bytes of `LOADER_PROLOGUE` and installs the trampoline at once: the table is read during loading, so there is no boot grace and nothing but the ini read ahead of it on the `desert-harvest` thread. Log: `[gimmick] record loader at +0x...`.

The callback runs on whichever game thread loads a record, before the deserializer reads it. `idx` arrives in `r8w`, masked with `0xFFFF`. From the manager: record count `+0x08`, offsets table `+0x28` (`u32` file offset at entry+4, records contiguous in index order), loaded-object array `+0x58`. From the stream: buffer, size and cursor, at offsets the hook reads off the game's code rather than hard-coding them (`+0x10`/`+0x18`/`+0x1C` on 25477059 and earlier, `+0x20`/`+0x28`/`+0x2C` on 26361232). At install `gimmick::parse_stream_fill` reads them from the accessor's fill sequence, the three stores into the stack stream before `lea r9,[rsp+0x30]`, into a `StreamLayout`; if that fails, `gimmick::choose_layout` probes the known layouts on the first call (buffer non-null, size in range, cursor equal to the offsets-table entry). With no layout that validates, the hook patches nothing and dumps nothing, and says so once (`[gimmick] stream layout unknown on this build`). The record bytes are copied out and the record header parsed. It has two shapes (`gimmick::HeaderShape`): `KeyFirst` through 25477059, `u32 key, u32 name_len, name, 0x00`, and `NameFirst` on 26361232, `u32 name_len, name` (no terminator), `u32 key, u8 0, u32 path_len, path, u8 flag` (flag 0 on 11511 records, 1 on 2699). Keys did not change. `gimmick::detect_header_shape` decides which one the table uses (the two shapes can never both validate), the hook latches it once and logs `[gimmick] record header: ...`, and `parse_header_as` reads every record in that shape. A header that does not parse leaves its record vanilla and is counted on the `[stat]` line (`headers unparsed N`); if none parses at all, `[gimmick] WARN no record header parsed in N records` says so once. The record is then classified by key against `desert_core::collect`, and `gimmick::multiply` returns the `u64` min/max edits, written back with `safe::write`.

**One hook is enough**: the record deserializer has exactly one reference in the image, the call inside the loader, and every code reference to the `"gimmickinfo"` string is accounted for (`docs/reference-internals.md` §19.6). The caveat is the preload path, which starts its cursor at 0 instead of consulting the offsets table, so the hook's `cursor != offsets[idx]` guard depends on records staying contiguous. If that breaks, the failure is silent and total for that pass: one `[gimmick] idx N: stream cursor ...` line and every record vanilla, no crash. **After a game update that is the first line to check.**

The stream buffer is freed about 2 s after the last load and reallocated on demand, so patching happens per record inside the hook. The hook's only shared state is atomics: it reads its settings from `config::LIVE`, a struct of atomics the plugin thread publishes into, so a change reaches the next record with no lock. It never calls a game function and returns vanilla on any failure.

## Re-apply

Every gather record's vanilla min/max and item id per output block, and its index, are kept in `remember`, a fixed lock-free table of atomics. After an `[ini] reloaded:` line, `hook::reapply` on the plugin thread walks that table through the game's record manager and writes `vanilla * multiplier` into the already-parsed objects, checking each record's key and block's item id first. The parsed object's layout is found, not assumed. `gimmick::ParsedLayout` has two known layouts: `OLD`, through 25477059 (key `+0x08`, list pointer `+0x278`, count `+0x280`, 16-byte entries with the key field at `+8`; `docs/reference-internals.md` §16), and `NEW`, 26361232 (key `+0x10` with a second copy at `+0x44`; a pointer at `+0x128` to a 16-byte list header `{u64 entries, u32 size, u32 cap}`; 16-byte entries with the block pointer at `+0` and a zero key field at `+8`). Blocks are the same in both: item `+0x68`, min `+0x20`, max `+0x28`. `reapply` tries them in order and accepts one only if it validates against every remembered record (key, count, item id, and a current min/max that is one whole multiple of vanilla); then it falls back to `gimmick::probe_parsed_layout`, and under `Debug=1` to `gimmick::find_item_paths`, a bounded pointer search that prints the path from a record object to its item and hex windows of an object, an entry and a block. It logs `[live] parsed layout: ...` with the result, or `[live] WARN parsed layout not found (...)` and writes nothing. The load-time patch never depends on it: it writes the raw bytes before the game parses them. Under `Enabled=0` records are read but not written at load, and a re-apply writes vanilla back.

The ini is shared, so its mtime moves for other sections' keys too, and `[Harvest]` holds the looter's keys as well. The harvest loop compares the yield half of what it just parsed with what it is running on and re-applies only when that moved; otherwise a looter slider drag would re-apply every record once a second.

## Yield model

Measured in game on build 25116796 on a `Foraging` node: a gather pays out **one** of the record's output blocks, apparently at random, rolled between that block's min and max. Multiplying every block scales the whole distribution. Single-block records (firewood, ore) follow by the same arithmetic but `Logging`, `Mining` and `Ore` have not been observed in play. Measure with the looter's `LogReceived=1` (`[recv]` lines), not with the `[gimmick]`/`[live]` lines, which show only what was written.

## The catch hook

`Bugs`, `Fish` and `Critters` are not gimmickinfo: a creature caught by hand is a character, and the amount granted is a hard-coded `mov r8d,1` (`docs/reference-internals.md` §17). `catch.rs` scans for the 21-byte `CATCH_SITE` (must hit once), checks the 13 bytes it will overwrite, and installs a stub from `desert_core::trampoline::count_hook_stub` through `hook::install_raw` that **replaces** the immediate with its callback's return value. The callback reads the actor's type and class bytes through `safe` and decides first by species: `species.rs` stores a `SpeciesClass` per characterinfo row from the generated `desert_core::species_table` (`just gen-species`; a bag catch is an `Insect_Catch` record with a convert item, classed Bug/Fish/Critter by its tribe group), and `creature::catch_class_by_species` answers from it, so ducks and raccoons (`NotHandCatchable`) are never multiplied (the table also carries `Body`, `FriendlyBody` and `Protected` rows, which the looter uses and the catch hook treats as not catchable). Only a species the table does not know falls back to the class-byte lists (`BUG_CLASSES` etc.). It returns 1 for anything that is not a recorded bug, fish or critter. A game update that moves this site disables only this hook, with a `[catch]` line.

## Table dump

`DumpTable=1` together with `DryRun=1` copies the whole table body from the loader's stream buffer, once per session on its first call, to `DesertTooling.gimmickinfo.bin` (`dump.rs`). `DryRun=1` is required because with multipliers live the copy could hold already-multiplied records. It is a diagnostic copy of what the loader saw; the offline tools do not read it, they read the game's archives (see [Re-targeting and analysis tools](retarget.md)), whose `gimmickinfo.staticinfobody` is byte-identical to a vanilla dump.

DMM's Desert Gatherer pack (`desert-gatherer-dmm/`, generated by `dmm-pack`) and DMM's built-in gathering multiplier edit the same scalars on disk; mounting either with this plugin multiplies yields twice.
