# Re-targeting and analysis tools

Sources: `CLAUDE.md` (Re-targeting after a game update, Analysis tooling), `crates/tools/README.md`, `crates/tools/src/bin/retarget/`, `justfile`, `docs/findings/2026-11-01-build-26345091-retarget.md`. Evidence: `docs/reference-internals.md` §19 and §19.5.

Every tool here is a Rust binary in `crates/tools/`, built by `just tools`, offline, and seconds per run on the 330 MB exe. [Tools](../repo/tools/index.md) is the full manual. Ghidra is no longer part of the workflow: a fresh auto-analysis of this exe takes far longer than a whole re-target with these tools, and the last two re-targets used none.

## After a game update

The plugin finds everything by content, so an update breaks it only where the compiler's output changed under a byte pattern. The game's data comes from the game's own archives (`<install>/<group>/0.pamt` and `<n>.paz`), read offline by `crates/tools/src/paz.rs`; nothing reads from the DMM tool and no step needs a `DumpTable` launch. The DMM pack is still shipped; it is generated, not rebased. The procedure is a checklist:

1. `just extract-tables`, then `just tools-check-game`. The first writes every static-info table (`.staticinfobody` and `.staticinfoheader`, 274 files on 26480954, as on 26423880 and 26361232) out of the archive into `analysis/tables/`; the second proves the reader still parses the new index (`paz_real`: byte identity with `analysis/tables/`, the gimmickinfo flags and sizes, the record split) alongside the other real-data tool tests. If the index format moved, this is where it shows, before anything else is trusted.
2. `just retarget report`, the pin check. One markdown page: the headers, every signature's hit count, the accessor census, and a table of the constants that have to move. `Verdict: clean` means nothing does; otherwise it says what.
3. For each dead signature, `just retarget triage`. It prints the longest prefix and suffix of the old pattern that still hit, and the function start a suffix implies. Then, on what is left:
   - `retarget calls <rva> <len> [--callers]`: every `E8`/`E9` target in a range, with its `.pdata` status, its first bytes, an auto-wildcarded pattern and that pattern's exe-wide count. `--callers` adds each target's distinct calling functions.
   - `retarget callers <rva>`: every reference to an address grouped by the function it is in, with a pattern per function.
   - `retarget prologue <rva> [--stolen K] [--tokens]`: whole instructions, the RIP and branch flags, and the safe stolen-byte counts (at or past 12, before the first RIP-relative or branch instruction). `--stolen K` checks one and prints the bytes for a `*_PROLOGUE` constant, exit 2 if unsafe.
   A new signature is accepted only at an exe-wide count of 1, and only after the function's identity is confirmed.
4. `just retarget census`. The accessor template the gatherer and dispatch reach every table through: the four heads, the tail after each, the slot load and its bounds-check register, the loader-call shape and distance, the loader prologue, and whether each table name is in `crates/tools/static-info-names.txt`. `--sites` prints one row per site. Its numbers are what `crates/desert-core/src/gimmick.rs` and `crates/desert-core/tests/gimmick_real.rs` are written against, and `crates/tools/src/bin/retarget/expect.rs` pins them.
5. `just test-game`. It reads the extracted tables in `analysis/tables/` (or `CD_TABLES`), so it runs right after step 1: the gimmick record header shape, the output blocks, and `gimmick::multiply` doubling every `collect.rs` row against the vanilla min/max in the archive table. A failing pin on an address is a re-pin, not a broken plugin, when the plugin resolves at runtime.
6. Re-pin the walk calibrations from the extracted body (`gen-collect-names` `CALIBRATION`, `items` `EXPECT_*`, `paths::CALIBRATED_BUILD`), never override them. Then run `gen-collect-names`, which reads the archive and derives every gather family from the records (the rule is in `crates/tools/src/bin/gen-collect-names/classify.rs`), and diff `crates/desert-core/src/collect.rs`. A row that appears or disappears is either a game change or a decode that moved; the generator prints the fields behind each one. If a decode no longer validates, re-read the deserializer fields it names before changing anything. Then `just dmm-pack` regenerates the DMM pack from the same table and `collect.rs`; diff `desert-gatherer-dmm/` and bump the pack's version. Then the other generated tables in `desert-core`, each read straight from the archives and each rewriting its whole file: `just gen-species` (`species_table.rs`), `just gen-containers` (`container_table.rs`), `just gen-dropsets` (`dropset_table.rs`) and `just gen-quest-items` (`quest_items.rs`, the item-log filter's quest and key items); diff each, and read the counts in its header against the catalogue diff.
7. Display names come from `analysis/strings/gimmick.eng.tsv`, which the archive reader cannot produce (`.paloc` is encrypted). Refresh it with the PazDump oracle only if the generator reports a row without a name.
8. One confirmation launch with normal settings, then read the log (see below). No `DumpTable`, and `DryRun` is not needed.
9. Write the findings note, `docs/findings/<date>-build-<id>-retarget.md`, from the report, and the `docs/reference-ledger.md` rows for every anchor that moved.

The first lines of `DesertTooling.log` to read, all `[harvest]`, in this order: `[gimmick] record loader at`, `[gimmick] stream layout: ...`, `[hook] record loader ... -> stub`, `[catch] hook at`, `[sig] N found, 0 missing`, `[hook] area_sweep`, `[hook] enqueue`, `[hunting] loot_grant`; then the `[dispatch]` slot lines, its `verdict` and `[banking]`; `[gimmick] record header: ...`; and the `[stat]` line, where `stream unread` and `headers unparsed` should be 0 and `recognised` non-zero. Any `[gimmick] idx N: stream cursor ...` line means every gimmick record was left vanilla for that pass.

The 2026-11-01 update is the worked example: the retarget was derived on build 26345091, and Steam shipped 26356046 and then 26361232 the same day. Each hotfix cost one `just retarget report` and a re-pin of the tests (on 26361232 every signature moved by the same 0x50 and nothing needed re-deriving), which is what "a checklist" is meant to mean. The 2026-11-04 update to 26423880 was the same again: every signature hit once, the census did not move, and the plugin side was a pure re-pin, while the table side took the catalogue diff and two record layouts that grew (`docs/findings/2026-11-04-build-26423880-retarget.md`). The 2026-11-06 update to 26480954 was a pure re-pin on both sides: the tables changed, but no generated file changed a row (`docs/findings/2026-11-06-build-26480954-retarget.md`).

## Function boundaries without Ghidra

`retarget` takes function starts from the PE exception directory: data directory 3, an array of `RUNTIME_FUNCTION` records, with chained cold fragments followed to their parent (`crates/tools/src/funcs.rs`). A leaf function with no unwind data falls back to a prologue-shape heuristic, and every start printed says which source it came from.

**Never find anything by section name.** This exe scrambles them on every build, hotfixes included: the exception directory has been `.link` (25246367), all of `.trace` (25477059), `.edata` (26345091), `.rdata` (26356046), `.shared` (26361232), `.edata` (26423880) and `.shared` again (26480954). `just retarget pe` prints the sections, the sixteen data directories and the exception directory's range and entry count (248753 on 26480954, 248726 on 26423880, 248667 on 26361232, 248666 on 26356046), and replaces the Python snippet that used to live in `CLAUDE.md`.

## The other offline tools

- **Table source**: the game's archives, through `paz::Archive` (group `0008` first, every group scanned if a path is not there), or `--tables DIR` for the extracted copies `just extract-tables` writes. `paz list` and `paz cat` read any plain entry; an encrypted one is refused.
- **Pinned calibration**: `gen-collect-names` (`CALIBRATION`) and `items` (`EXPECT_*`) refuse a table that does not match their build's counts and anchors. After an update, re-pin; never override.
- `just sigscan`: every signature must hit once and every static-info type name occur once (221 names on 26480954, as on 26423880 and 26361232). It always exits 0; `retarget triage` is the one with an exit code.
- `xrefs <rva>`: rel32 calls and jumps, RIP-relative `lea`/`mov`, and pointer cells holding the VA. `--selfcheck` diffs against the reference loop. One REX instruction reads as two references.
- `dis <start> <end>`: disassemble an RVA range, addresses as RVAs (add `0x140000000` for the VA).
- `fieldnames`: field names of every static-info record class from the game's Korean per-field read-failure strings, into `analysis/fieldnames.json` (§19.9).
- `sigscan` prints **file offsets**, `xrefs` and `dis` take RVAs. `retarget` takes either (`f:` marks a file offset) and prints RVAs.

## Appendix: Ghidra and `just evidence`

Optional, and only for `just evidence`, which exports one Markdown file per function into `evidence/` over GhidraMCP's HTTP API. `evidence/` as it stands is the frozen build 25116796 reference and is still useful to grep for what an old function did; nothing in the re-target needs it regenerated.

Ghidra runs on Windows with the upstream GhidraMCP extension, which binds the wildcard address so WSL reaches it on the host IP; GhidraMCP reads its port (8081 here) once at plugin construction and logs `BindException` to `application.log` if it is taken. "Connection refused" is the HTTP side; "Connection closed" is the `ghidra-mcp-bridge` process dying at launch, which must be in `environment.systemPackages`. Two traps in the project itself: `searchFunctions` cannot find a string constant (grep `evidence/` instead), and every function's phantom `[DATA]` xref is its own `RUNTIME_FUNCTION` record (§19.5).
