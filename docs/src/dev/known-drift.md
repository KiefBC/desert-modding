## Generated, forward-looking

- **Release links name the next release.** The `Tagged` column in `VERSIONING.md` and the release links in the root `README.md` carry `<crate>-v<semver>` strings that `just sync-versions` writes from `Cargo.toml`. While the plugin is ahead of its last tag they name a tag that does not exist yet. Do not hand-edit them; `just check-versions` fails if they drift from `Cargo.toml`. The same tool owns the `**Version x.y.z**` line at the top of `crates/desert-tooling/README.md`. It never scans `docs/src`, which is why the fresh chapters of this book carry no versions.
- **`evidence/README.md`** says it was generated by the retired Python `evidence.py` against build 25116796. It is regenerated whole by `just evidence` (template in `crates/tools/src/bin/evidence/tree.rs`, which already says `just evidence`); the tree has not been re-exported since and, with Ghidra out of the re-target procedure, is kept as the frozen 25116796 reference. Never hand-edit it.

## Measured on an older build

- **The `[banking]` gates** (dispatch) were read off on builds 25116796 and 25246367 from saved logs. Since 0.10.0 they resolve by signature (`node::globals`), `0x7150E18` / `0x7128CA8` on 26356046 and on 26361232. Both read `0` in game on 26361232 (the 2026-11-01 dry runs, again at 18:46 UTC); no log from 25477059 or 26356046 was ever read, so their values there are unmeasured. The wording in `crates/desert-dispatch/src/config.rs` and `DesertTooling.ini` says "measured so far" for that reason, and its build list there still reads (25116796, 25246367).
- **The dispatch layout is static-only except where one launch confirms it.** `docs/reference-internals.md` section 20.19.1 re-derived it from code on 26345091 and 26356046 (26361232 was not re-read for it; `banking_real` passed unchanged there); `REC_KEY` and the condition element layout are UNCONFIRMED there (`ROW_WEIGHT_SUM`, `rec+0x38`, is CONFIRMED-GAME since the 18:15 UTC launch on 26361232: 221/221 fully read rows matched `record+0x38`), and the census values in section 20.19's table are 25477059's. The write gate (`node::WriteGate`) keeps a wrong offset from writing; the `[sum]` and `[rewards]` verdicts and `weight totals: N/N` of one launch confirm it. On 26361232 the launches printed both verdicts `LOOKS RIGHT`, 939/939 missions and weight totals 221/221, and at 18:46 UTC `[dry] missions back to vanilla: 939 entries visited ... 0 changed` and `[dry] rewards back to vanilla: 221 of 221 rows ... 0 changed`.
- **The walk calibrations are re-pinned to 26361232** from the 18:46 UTC dump: `paths::CALIBRATED_BUILD`, `gen-collect-names` `CALIBRATION` (581 lists / 904 blocks / 14210 records), `items` `EXPECT_*` and DMM pack 1.3 all describe the 26361232 table now, as `expect.rs` (`BUILD`) and the real-exe tests already did. They are re-pinned from the game's own table bytes, never from a guess.
- **The gimmickinfo record header has two shapes.** `KeyFirst` (`u32 key, u32 name_len, name, 0x00`) through 25477059, `NameFirst` (`u32 name_len, name, u32 key, u8 0, u32 path_len, path, u8 flag`) on 26361232; 26345091 and 26356046 were never dumped, so which build first changed it is not known. The plugin (`gimmick::detect_header_shape`) and the offline tools (`crates/tools/src/records.rs`) read both and latch the one they find. Anything that walks or quotes record offsets from before 26361232, including the findings notes, uses the key-first shape.
- **The record loader's stream layout is parsed, not pinned.** Buffer / size / cursor sit at stream `+0x10`/`+0x18`/`+0x1c` on 25477059 and earlier and at `+0x20`/`+0x28`/`+0x2c` on 26361232 (two new zero qwords at `+0x10`/`+0x18`); 26345091 and 26356046 were never launched, so which build first moved them is not known. Since the fix `gimmick::parse_stream_fill` reads the layout off the accessor's fill sequence at install and `gimmick::choose_layout` probes the known layouts if that fails; `retarget census` prints the `stream fill:` line and `expect.rs` pins `STREAM_LAYOUT` (0x20, 0x28, 0x2c). The first 26361232 launch, before the fix, read zeros at the old offsets, refused the dump and patched 0 records (`docs/findings/2026-11-01-build-26345091-retarget.md` §7.7).
- **The parsed record layout is probed, not pinned.** `gimmick::ParsedLayout` knows `OLD` (through 25477059: key `+0x08`, list `+0x278`, count `+0x280`) and `NEW` (26361232: key `+0x10`, list header pointer at `+0x128`); `reapply` validates each against every remembered record, then falls back to `gimmick::probe_parsed_layout` and, under `Debug=1`, `gimmick::find_item_paths`. Closed 2026-11-01: launch 8 logged `[live] parsed layout: key +0x10, list +0x128 -> +0x0, ...` and eight slider moves with `0 skipped` (findings note §7.10). 26345091 and 26356046 were never launched, so which build first moved it is not known.
